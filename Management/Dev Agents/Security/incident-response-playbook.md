# Incident Response Playbook — One
**נוצר**: 2026-10-22
**עדכון אחרון**: 2026-10-22
**מטרה**: מדריך לטיפול באירועי אבטחה. מתעדכן אחרי כל אירוע עם לקחים ופתרונות.

---

## עקרונות כלליים
1. **מידע משתמשות קודם לכל** — חוסמים גישה לנתונים לפני שדואגים לרציפות שירות
2. **שלב-שלב** — לא מחליפים הכל בבת אחת. סוד אחד → בדיקה → הבא
3. **לא מחזירים מפתח שבוטל** — גם אם שבר משהו, מתקנים קדימה
4. **תיעוד בזמן אמת** — שעת ביצוע, תוצאה, בעיות שצצו
5. **הודעה למשתמשות לפני שמתחילים** — לא אחרי שכבר שברנו משהו

## סוגי אירועים

### אירוע 1: חשיפת Environment Variables (ספק תשתית)
**דוגמה**: פריצת Railway אוקטובר 2026

**סדר פעולות:**
1. **הערכה** — קרא את ההודעה. האם זו הודעה כללית או אישית? מה בדיוק נחשף?
2. **מיפוי** — רשום כל סוד שנשמר אצל הספק. סווג: קריטי (גישה לנתונים) / בינוני (שירות) / נמוך
3. **גיבוי** — `pg_dump` מלא לפני כל שינוי
4. **בדיקת פעילות חשודה** — לוגים אצל כל ספק, חיובים, התחברויות
5. **הודעה למשתמשות** — באנר + הודעה במסך login
6. **החלפה מדורגת** — לפי סדר עדיפות (DB → Auth → API keys)
7. **בדיקות אחרי כל שלב** — checklist מוגדר מראש
8. **סגירה** — ביטול מפתחות ישנים, הסרת באנר, תיעוד

**סדר עדיפות החלפה:**
| עדיפות | סוג | דוגמאות | סיבה |
|---------|------|---------|-------|
| 1 | גישה ל-DB | DATABASE_URL, סיסמאות Postgres | גישה ישירה לכל המידע |
| 2 | Auth secrets | JWT_SECRET, SERVICE_ROLE_KEY | זיוף זהויות |
| 3 | API keys עם גישה למידע | Supabase service role, Storage | גישה לקבצים/נתונים |
| 4 | API keys לשירותים | OpenAI, Resend, Firebase | שימוש על חשבוננו / spam |
| 5 | מפתחות צד שלישי | GitHub tokens, registries | תלוי בהרשאות |

## מה לא להחליף

- הגדרות תצורה (PORT, NODE_ENV)

## Android — מה לזכור
- האפליקציה מבוססת Capacitor עם `server.url` → joinone.io
- כל הסודות בצד השרת — שינוי env vars לא דורש גרסה חדשה בחנות
- `VITE_SUPABASE_ANON_KEY` מוטמע ב-client אבל ציבורי — לא צריך החלפה
- **אם אי פעם נצטרך להחליף ANON_KEY** — חובה לשחרר גרסה חדשה ב-Google Play לפני ביטול הישן

## לקחים כלליים (מתעדכן)

### מהפריצת Railway (2026-10-22):
- **Railway image push יכול להיתקע** — הפתרון: שינוי variable ידני triggers restart ללא build חדש
- **DATABASE_URL reference לא triggers redeploy** — כש-Postgres service מחליף סיסמה, ה-app service לא תמיד עושה redeploy אוטומטי. צריך trigger ידני.
- **להתחיל מסודות בלי השבתה** (API keys) ולהשאיר DB/auth לסוף — ככה גם מוודאים שדיפלויים עובדים
- **באנרים למשתמשות לפני שינויי DB** — הכנה מראש עם כפתור dismiss
- **Supabase מפתחות חדשים (sb_secret_...)** — לא ניתן לעשות regenerate פשוט, צריך מעבר מתוכנן
- **בדיקת לוגים קודם** — OpenAI usage, Resend logs, Supabase Auth. מורידה לחץ ומאפשרת תעדוף נכון
- **לא לשנות הכל ביחד** — שלב אחד, בדיקה, שלב הבא
